# market-alpha-agents

A local, multi-agent research system that analyzes US equities, Japanese equities (TSE), and major crypto to produce **manual decision-support** for day/swing trading: a scored buy/sell/hold call per ticker with a suggested holding period, profit target, and stop-loss, plus the reasoning behind it. It never places or auto-executes trades — every recommendation is meant to be read by a human and acted on manually.

Status as of 2026-08-31: **planning complete; Phase 0 done; Phase 1 (data layer) further along (8 of ~13 connectors + the Parquet/DuckDB analytical store built); Phase 2 (specialist agents) all 8 directional agents done end-to-end; Phase 3 (supervisor/aggregation) done for equity AND crypto (crypto graph wiring complete); Phase 4 (backtesting/validation) all 6 remaining signals attempted and honestly reported, plus a real DSR/PBO/MinTRL graduation gate; Phase 5 (news/alerting) FinBERT triage + Discord/email channels + unlock/Fear&Greed triggers added; Phase 7 (human review workflow) built — the interrupt()/approval gate that was previously missing entirely is now live and enforced structurally, not just by convention.** See "Where things stand" below for exactly what's built, tested, and next.

**You can run the whole system today:** `python scripts/run_daily_scan.py` runs every US/JP/crypto watchlist ticker through the full specialist pipeline and logs each recommendation to `storage/recommendations.db` — but as of the Phase 7 gate, it no longer sends any alert itself. Every recommendation pauses at a real `interrupt()`; `python ui/review_cli.py approve|reject <recommendation_id>` is the only code path that can ever cause an alert to fire. Just ran the whole thing for real against the actual configured watchlist (12 tickers across all three asset classes) — see "Where things stand" for the result.

**LLM provider note:** the plan originally specced local Ollama as primary. Per direction, this was switched to the **Rakuten AI Gateway (Claude)** instead, reusing the same live-verified client construction as `../Server_failure/rakuten-failure-agent` (gateway auth via header, not `api_key`; no `temperature` param; `max_tokens=128000`; streaming required). Ollama (`qwen2.5:7b`, already pulled locally) is now the configured fallback, not primary. See `agents/llm_client.py`.

## Read this before anything else

- **Not licensed financial advice.** This is a personal, single-operator research tool. See `docs/plan/section_risk_validation.md` §8 for Japan-specific tax/compliance notes (crypto and equities are taxed very differently; J-Quants data may not be redistributed or used to advise third parties).
- **The 50%+ return target is an aspiration, not a design goal.** `docs/plan/section_risk_validation.md` §7 lays out the honest case for why: full-population studies of retail day traders (Brazil, Taiwan) show ~97% of persistent day traders lose money; a well-validated systematic strategy that survives years typically runs Sharpe ~1-2 and CAGR ~15-40%/year, not 50%+ in months. Anything claiming better should be treated as probable overfitting until it survives the validation gauntlet in §4-§5. Success for this project should be defined as *capital preservation + demonstrated statistically-significant edge*, with 50%+ as a low-probability tail outcome, not the base case.
- **Free-tier data has real gaps.** Most notably: Glassnode's free API tier was discontinued sometime before this research (Aug 2026) — the on-chain agent runs on weaker data than originally hoped (see `docs/plan/section_data_pipeline.md` §1). Japanese equities have exactly one live data source with no real fallback. Both are called out explicitly rather than papered over.

## How this was built

The research and plan were produced by a multi-agent workflow, not written by hand:
1. **8 parallel research agents** investigated technical-analysis strategies, crypto-specific factors, multi-agent orchestration architecture, and free-tier data sources for US/Japan/crypto (`docs/research/*.md`).
2. **4 section-drafting agents** turned that research into the plan sections below (`docs/plan/section_*.md`).
3. **A critique agent** red-teamed the four drafts against each other and found 12 concrete defects — contradictory logic between two sections, a missing Japan-specific risk check, a formula bug, an uncited regulatory claim, etc. (`docs/plan/critique.md`).
4. **4 parallel fix agents** applied surgical, critique-driven corrections directly to the sections.
5. Manual follow-up caught and fixed one more issue the automated pass missed (Glassnode's free tier being gone, which the on-chain agent's spec still assumed) — a reminder that this whole pipeline needs a human checking its work, which is exactly the posture the system itself is designed around.

## Agent roster at a glance

Every specialist outputs a `signal_score` (-1 to +1), a `confidence`, and rationale; `RiskManagerAgent` and `MarketRegimeAgent` are gates/modifiers, not directional votes; `PortfolioSupervisorAgent` deterministically blends everything into one final call (full algorithm in `section_agents.md` §10).

| Agent | Examines |
|---|---|
| MeanReversionAgent | Bollinger fade, RSI-2, VWAP reversion, z-score vs moving average |
| TrendMomentumAgent | MA crossovers, ADX, Donchian breakout, MACD, cross-sectional momentum vs. broad-market benchmark |
| SeasonalityAgent | Day-of-week/month, PEAD, sector seasonality |
| ShortSqueezeAgent | Short interest, days-to-cover, borrow-fee spikes, unusual options volume (US full, JP degraded, N/A crypto) |
| VolatilityVolumeAgent | ATR expansion, relative volume, volume profile — confirms/denies other agents, never directional alone |
| CryptoOnChainAgent | MVRV, SOPR, exchange flows, whale cohorts, unlock schedules, staking yield (crypto only) |
| CryptoDerivativesAgent | Funding rates, open interest, liquidation clusters, options skew (crypto only) |
| NewsSentimentAgent | LLM-scored headline sentiment, recency-weighted |
| RiskManagerAgent | Position sizing, structural feasibility (TSE lot size, PDT/margin rules), TSE price-limit-band risk, correlation cap, drawdown circuit breaker, veto power |
| MarketRegimeAgent | System-wide position-size-ceiling multiplier based on trailing realized-volatility percentile |
| PortfolioSupervisorAgent | Deterministic aggregation of all of the above into one auditable call |

**Phase 4 (Backtesting & Validation) — framework built and applied to one signal for real:**
- `backtesting/robustness.py` — Sharpe, profit factor, max drawdown, Calmar ratio (hand-fixture-tested), plus Deflated Sharpe Ratio, Probability of Backtest Overfitting (via combinatorial cross-validation), and Minimum Track Record Length, all implemented directly from Bailey & López de Prado's published formulas. **Honesty note:** no independently-sourced worked numeric example existed to hand-verify DSR/PBO/MinTRL against, so those three are tested against documented monotonicity/sanity properties (e.g. pure-noise variants → PBO≈0.5, a genuinely-best variant → low PBO) rather than exact fixtures — a real but weaker form of verification, flagged rather than presented as equivalent to the hand-computed tests elsewhere in this repo.
- `backtesting/walk_forward.py` — rolling (not anchored) walk-forward split generator, hand-fixture-tested.
- `backtesting/run_backtest.py` — vectorbt-backed position/equity-curve simulation with realistic fees/slippage. Found and fixed a real compatibility bug live: vectorbt 1.1.0 (current as of Aug 2026) crashes on import against plotly≥7 (a renamed trace name), and separately, vectorbt's own `sharpe_ratio()` accessor throws on a business-day-indexed series ("BusinessDay is a non-fixed frequency") — worked around by using vectorbt only for trade simulation and routing every statistic through `robustness.py` uniformly, not vectorbt's stats API.
- **Real result, not synthetic:** ran a full walk-forward backtest (12-month in-sample / 3-month out-of-sample, rolling) of `MeanReversionAgent`'s signal against 8 years of real AAPL data (2018-2026), reporting only the concatenated out-of-sample segments. Result: **Sharpe -0.40, profit factor 0.80, Deflated Sharpe 0.0** — this specific signal, at its current default thresholds, shows no real edge on this ticker once realistic costs are applied. That's the validation framework doing its job (rejecting a mediocre backtest), not a failure of this phase.
- Added `mean_reversion_signal_series()` (vectorized full-history version of the same formula `compute_mean_reversion` uses on the latest bar) and cross-validated it against the scalar function at multiple truncation points — they agree exactly.
- **The other 6 signals, all attempted, all reported honestly (no cherry-picking, no fabricated results):**
  - `TrendMomentumAgent` — real edge found: 8.6 years of real AAPL/SPY data, 30 walk-forward splits, 1890 OOS days → **Sharpe 0.67, profit factor 1.21, Deflated Sharpe 0.97** (passes the config gates). A genuinely different result from `MeanReversionAgent`'s null one, consistent with AAPL's real 2018-2026 uptrend — not tuned to get here.
  - `SeasonalityAgent` — real backtest, **zero trades ever entered** across 8 years: the signal is hard-capped at `|score|<=0.3` by its own design and never crosses the default 0.35 buy threshold. An even starker "no standalone edge" result than `MeanReversionAgent`'s, exactly matching its documented role as a caution-tilt overlay, never a trigger.
  - `VolatilityVolumeAgent` — **correctly concluded not backtestable in this form**, not forced into one: its real output is `vol_conf_multiplier`, a non-negative confirmation/gating scalar with no sign or threshold-crossing structure, and its secondary `signal_score` is literally `sign(this bar's own return)` — running it through a buy/exit-threshold backtest would just test "did today already close up," a tautology, not a forecast. No code was written rather than manufacture a number that looks like validation but isn't.
  - `CryptoDerivativesAgent` (funding-only) — real backtest using real BTC/USDT funding-rate history (3,283 real 8h prints via a new `CCXTSource.get_funding_rate_history`, paginated) and real BTC/USDT price history: **Sharpe -0.62, Deflated Sharpe 0.15** (fails the gate) — no edge from funding alone. `oi_score`/`skew_score` are excluded from this backtest: Binance's free open-interest-history endpoint live-verified to reject any `since` older than ~30-45 days, far short of what a real walk-forward split needs.
  - `ShortSqueezeAgent` and `NewsSentimentAgent` — **correctly found not backtestable at all with sources already in this codebase**, and said so precisely rather than skipping quietly: `ShortSqueezeAgent` needs historical short-interest/borrow-fee/options-chain series that no connector here provides even a snapshot history for (yfinance's `Ticker.info` gives exactly two point-in-time short-interest values, ~1 month apart, never a series); `NewsSentimentAgent` needs a multi-year headline archive (RSS has none by protocol design, Finnhub's real archive only reaches back to ~mid-2025) and its sentiment scoring is live-LLM-based, not a fixed formula, so "backtesting" it would mean re-running a non-deterministic LLM over history — a fundamentally different exercise from the formula-only backtests above.
- **`backtesting/graduation_gate.py`** — the real pass/fail checklist from `section_risk_validation.md` §4: `evaluate_strategy()` checks Deflated Sharpe / PBO / MinTRL (both the config floor and the statistically-dynamic requirement) / profit factor > 1.5 against `config.yaml`'s real `robustness_gates`, and deliberately does **not** gate on max drawdown/Calmar — the doc's own word for those is "eyeballed," not a numeric cutoff, so the gate surfaces them for a human without failing on them.
- **A real multi-variant parameter sweep, not synthetic** (the doc's own explicit requirement, distinct from `robustness.py`'s sanity tests which use synthetic variants): 5 real `MeanReversionAgent` variants backtested on real AAPL data, fed into `probability_of_backtest_overfitting` → **PBO = 0.679**, above the config's `max_pbo=0.4` ceiling. Feeding the best variant into `evaluate_strategy()` → **FAIL** — correctly rejected, not a bug in the gate.

**Not yet built (remaining Phase 4 work):** `bt`/`zipline-reloaded` (portfolio-level realism) and `freqtrade` (crypto leg) are explicitly not installed — see `pyproject.toml`'s `backtesting` extra for why. ## Phase 7 (Human Review Workflow) — the safety-critical gate, built and live-verified end to end

The plan calls this "the single most important regression test in the whole system": **no recommendation may ever reach `alerting/` without passing through a human-approval gate first.** Before this pass, that gate did not exist — `run_daily_scan.py` fired Telegram/desktop alerts directly off every trigger, with no approval step at all. Building this closed a real, live safety gap in an already-runnable script, not a theoretical one.

- `orchestration/graph.py` — added an `approval_gate` node between `supervisor` and `END` that calls LangGraph's `interrupt()` (live-verified against the installed langgraph 1.2.11's actual API before writing the integration, not assumed from the plan's pseudocode). Every graph run now pauses there; `supervisor_verdict` is already written by that point, but `human_decision` stays `None` until something explicitly resumes it via `Command(resume="approved"|"rejected")`. Added `resume_for_ticker()` as the one function allowed to do that.
- `orchestration/storage.py` — added `update_human_decision`, `init_outcomes_db`/`save_outcome`/`get_outcome` (`storage/outcomes.db`), and `pending_outcomes()` (the `recommendations.db` ⋈ `outcomes.db` join, excluding rejected/already-logged by construction).
- `ui/review_cli.py` — all three flows from the plan: `approve|reject <recommendation_id>` (resumes the paused graph, records the decision, and — approve only — sends the real alert, the *only* code path in this system that does); `log-outcome <ticker> <date>` (refuses to log against anything not `human_decision == "approved"`); `pending-outcomes --older-than <Nd>`.
- `scripts/run_daily_scan.py` — the direct alert-sending block is gone; it now only logs pending recommendations and prints which ones crossed a trigger, deliberately leaving the send decision to `review_cli.py`.
- **Structural regression test, not just a behavioral one** (`tests/test_orchestration/test_graph.py::test_graph_has_no_edge_from_supervisor_directly_to_end`): inspects the compiled graph's own edge list and asserts `("supervisor", "__end__")` does not exist and `("supervisor", "approval_gate")`/`("approval_gate", "__end__")` do — so this can't silently regress if a future edit adds a shortcut edge.
- **Ran the real thing end to end, no mocks**: a live `run_daily_scan.py` pass paused all 9 real recommendations at the gate; `review_cli.py approve AAPL-2026-08-31` resumed the actual paused graph from the real `orchestration/checkpoints.db`, recorded the decision, and fired a real desktop notification (Telegram no-ops cleanly since no bot token is registered yet); `review_cli.py reject MSFT-2026-08-31` recorded a rejection and sent nothing; re-approving `AAPL-2026-08-31` a second time was correctly refused.

**Not yet built:** the monthly `robustness.py` re-run against accumulating `outcomes.db` data (needs real outcomes to accumulate first — see Phase 6).
