# Multi-Agent Orchestration Architectures for a Local Trading-Research System (as of August 2026)

## 1. Orchestrator/Supervisor Design Patterns

**Hierarchical supervisor (recommended default).** One orchestrator agent owns the workflow: it dispatches sub-tasks to specialist agents (financial analyst, quant/technical trader, risk manager), receives their structured outputs, and produces the final recommendation. This is the dominant 2026 pattern in both LangGraph's official tutorials and Microsoft's new Agent Framework, and it maps naturally onto "manager reviews specialist reports" workflows. LangGraph's supervisor concept docs: https://docs.langchain.com/oss/python/langgraph/multi-agent (redirects/variants also at the LangGraph GitHub repo, https://github.com/langchain-ai/langgraph).

**Planner-executor.** A planning step decomposes the task ("today: refresh watchlist, re-score open positions, scan for new setups") into an executable plan, then a (possibly separate) executor loop calls tools/specialists step by step. Both LangGraph and Microsoft's Agent Framework distinguish "agents" (open-ended, autonomous tool use) from "workflows" (explicit, deterministic step graphs) and recommend workflows/planner-executor when "the process has well-defined steps" and "multiple agents must coordinate" — which is exactly a daily market-scan job. Source: Microsoft Agent Framework overview, https://learn.microsoft.com/en-us/agent-framework/overview/agent-framework-overview (page dated 2026-07-29).

**Blackboard / shared-state pattern.** A classical AI architecture (originating with Hearsay-II in the 1970s) where independent specialists read/write to a common shared workspace rather than talking to each other directly. In 2026 LLM systems this reappears as a typed shared "state" object (LangGraph's `State`/`Store`) or a shared memory/scratchpad that analyst, trader, and risk agents each read and append to. It's a good fit when specialists need each other's partial outputs but you don't want rigid point-to-point handoff wiring. LangGraph's persistence/store abstraction (see §4) is effectively a blackboard.

**Debate / voting aggregation.** Multiple agents (or multiple personas of the same model) produce independent judgments, then either (a) argue in structured rounds (multi-agent debate) or (b) vote/average. Two concrete 2026-relevant reference points:
- **Mixture-of-Agents** (Wang et al., arXiv 2406.04692): a layered proposer→aggregator architecture where each layer's agents condition on the previous layer's outputs before producing a refined answer — directly applicable to "financial analyst + quant + risk manager → synthesis agent."
- **TradingAgents** (Xiao et al., arXiv 2412.20138, latest revision v7, June 2025, and an actively maintained open-source implementation — see below) implements exactly this domain's version: Analyst Team (fundamental/sentiment/news/technical) → Bull/Bear Researcher **debate** (configurable `max_debate_rounds`) → Trader synthesizes the debate → Risk Management/Portfolio Manager team gives final risk-adjusted approval/rejection. This is a "staged consensus" model, not simple voting, and is the closest existing open-source blueprint to what you're building (financial-analyst / trader / risk-manager personas feeding one recommendation).

Reference implementation worth studying directly: https://github.com/TauricResearch/TradingAgents — built on LangGraph, ~100k GitHub stars, releases as recent as July 2026 (v0.3.1), so it is a live, actively maintained 2026 project, not an abandoned research demo. It is MIT-style open source and runs locally; it already implements the analyst→debate→trader→risk-manager pipeline you're designing, and its agent/state code is directly readable for adaptation (though it's built for a somewhat heavier/paid-LLM-usage pattern than a $650 free-tier hobby account, so budget/rate-limit tuning would be needed).

## 3. Agent-to-Agent Handoffs and Weighted Aggregation into One Decision + Confidence Score

Design pattern that combines the research above into something concrete for your three personas:

1. **Structured, typed outputs per specialist**, not free text — e.g., each of {financial-analyst, quant-trader, risk-manager} agents returns a JSON object: `{signal: BUY|SELL|HOLD, conviction: 0-1, rationale, key_risks, suggested_holding_period, target_price, stop_loss}`. This is the single most important practical recommendation: forcing structured output is what makes aggregation and confidence scoring tractable (both OpenAI's and LangGraph's docs stress this — "structured outputs to generate well-formed data" for downstream code-based orchestration).
2. **Handoff pattern**: use **agents-as-tools / manager-owns-final-answer**, not full handoff-of-control. Each specialist is invoked as a tool call by the supervisor and returns its structured verdict; the supervisor retains control throughout and never lets a specialist "take over the turn" (full handoffs are better suited to customer-support-style routing, not analyst aggregation).
3. **Debate round (optional but recommended, per TradingAgents)**: before final aggregation, run one adversarial round — e.g., a "bull" and "bear" pass over the same evidence — and feed both into the risk manager. This measurably reduces one-sided overconfidence versus a single pass per agent.
4. **Weighted aggregation into one score**: a simple, auditable formula beats an opaque LLM "vote" for a system a human must trust and act on manually. Practical approach:
   - Convert each specialist's signal to a signed score (e.g., BUY=+1, HOLD=0, SELL=-1) times its stated conviction (0-1).
   - Apply fixed, disclosed weights per persona (e.g., risk-manager weight can *veto* rather than just average — i.e., if risk-manager conviction on "SELL/avoid" exceeds a threshold, it overrides a numeric average regardless of analyst/trader enthusiasm). This mirrors TradingAgents' "Portfolio Manager approves or rejects" final gate rather than a naive average.
   - Compute overall confidence as a function of (a) weighted average conviction, and (b) **agreement/dispersion** across the three personas — if analyst says BUY 0.8 and risk-manager says SELL 0.7, confidence should drop even if the naive weighted average is positive. This "disagreement lowers confidence" rule is a cheap, non-LLM heuristic that meaningfully improves trustworthiness of the final number.
   - Log every component score (per-agent signal, conviction, and the aggregation math) alongside the final recommendation so the human operator can see *why* the score is what it is — critical for a manual-execution tool where you need to sanity-check the machine's reasoning before clicking "buy" yourself.
5. Academic grounding for the aggregation step: Mixture-of-Agents (arXiv 2406.04692) for layered proposer→aggregator synthesis; TradingAgents (arXiv 2412.20138, v7 June 2025) for the domain-specific analyst→debate→trader→risk-manager staged-consensus precedent.

## 4. Human-in-the-Loop Checkpoints (system must never auto-execute)

Both leading local-friendly frameworks have native, low-effort primitives for this — you don't need to build it from scratch:

- **LangGraph**: `interrupt()` pauses the graph at any node and persists exact state via its checkpointer; the run stays paused (potentially indefinitely, across process restarts) until you call `Command(resume=...)` with the human's decision. This is a clean fit for "pause after the risk-manager step, show the human the aggregated recommendation + confidence score, and require an explicit resume/approve/reject before writing the recommendation to the log or sending an alert." Source: https://docs.langchain.com/oss/python/langgraph/human-in-the-loop.
- **CrewAI**: per-task `human_input=True` flag pauses execution for the human to review/approve the agent's output before the crew continues. Source: https://docs.crewai.com/concepts/human-in-the-loop.
- **OpenAI Agents SDK**: guardrail "tripwire" exceptions plus a pre-approval hook on tool execution (`pre_approval_tool_input_guardrails=True`) that requires explicit sign-off before a tool (e.g., a hypothetical "place order" tool) actually runs. Source: https://openai.github.io/openai-agents-python/guardrails/.
- **Claude Agent SDK**: has a first-class **Permissions** system to mark specific tool calls as "always ask" vs. "auto." Source: https://code.claude.com/docs/en/agent-sdk/overview.

For your explicit "never auto-execute" requirement, the concrete recommendation is: **never even build an order-placement tool into the agent graph.** Don't rely solely on an approval gate around a trade-execution action — architecturally omit trade-execution capability from the agent's toolset entirely, and use the HITL/interrupt mechanism only to gate *lower-stakes* actions such as "send a push notification/alert" or "write today's recommendation to the log/dashboard." This is a stronger safety property than a permission check that could in principle be misconfigured.

## 5. State/Memory Management Across Scheduled Runs

For a daily market scan that must "remember yesterday's calls," the relevant distinction (made explicitly in LangGraph's docs) is:
- **Short-term / thread-scoped memory** via a **checkpointer** (LangGraph offers `InMemorySaver` for dev, `SqliteSaver` for local persistence, `PostgresSaver` for heavier setups) — this preserves the state of a single run/conversation, supports crash recovery and "time travel," but is scoped to one thread/run.
- **Long-term / cross-thread memory** via a **store** — an application-level key-value/document store that persists *independently* of any single run, intended for "user preferences, facts, and shared knowledge." For your use case: after each daily scan, write each ticker's recommendation, score, and rationale into the store (e.g., under a `symbol/date` key); on the next day's run, the analyst/risk-manager agents can be given a tool to read yesterday's (or last N days') entries for that symbol before producing today's verdict — enabling genuine "did we already flag this, did the thesis play out, are we repeating a mistake" continuity. Local persistence for this is trivial (SQLite file, or CrewAI's LanceDB-backed unified `Memory` class which already does semantic-similarity + recency-decay retrieval out of the box, described above). Source: https://docs.langchain.com/oss/python/langgraph/persistence, https://docs.crewai.com/concepts/memory.
- Practically: run the daily scan as a **new thread/session each day** (fresh short-term state, no stale conversational cruft) but always attach the same long-term store/database file, and give the orchestrator (or a dedicated "history" tool) explicit read access to prior days' structured outputs. This avoids two failure modes — a system with no memory (repeats the same "discovery" every day with no sense of how prior calls performed) and a system with one giant ever-growing single conversation thread (context bloat, harder to keep the LLM focused on today's decision).

## 6. Recommendation

**Primary recommendation: LangGraph as the orchestration backbone**, structured as a hierarchical supervisor graph with:
- Nodes for financial-analyst, quant/technical-trader, and risk-manager, each returning structured (Pydantic/JSON) verdicts.
- An optional bull/bear debate sub-step ahead of the risk-manager node (borrowing directly from the TradingAgents pattern).
- A deterministic Python aggregation function (not another LLM call) computing the weighted signal + confidence score with a risk-manager veto rule and a disagreement-based confidence penalty, for auditability.
- `interrupt()`-based human checkpoints before any alert/log-write action, and **no trade-execution tool anywhere in the graph**.
- SQLite-backed checkpointer for run-level durability and a simple SQLite/JSON store (or LangGraph's `Store` abstraction) for cross-day memory of prior recommendations, keyed by ticker/date.

Justification: it is fully open-source, runs entirely locally with zero mandatory paid service (LangSmith/Platform are optional extras you can skip), has mature, well-documented primitives for exactly the three hard problems in this task (multi-agent supervision, human-in-the-loop interrupts, and short/long-term memory separation), is model-agnostic (works with free-tier/local models, not locked to one vendor's paid API), and — most importantly for de-risking the build — it is the framework underlying TradingAgents, an actively maintained (July 2026 release), ~100k-star open-source project that already solves the analyst/debate/trader/risk-manager pipeline you're describing, giving you a real, current reference implementation to study or adapt rather than designing from a blank page.

**Reasonable alternative: CrewAI**, if you prioritize faster initial prototyping and want its newer unified, auto-scoped `Memory` class (semantic + recency + importance retrieval, persisted locally via LanceDB) largely "for free" instead of hand-rolling the store logic — at the cost of somewhat less fine-grained control over graph-level retries/branching than LangGraph gives you.

**Avoid for a new build in 2026:** Microsoft's original AutoGen (explicitly in maintenance mode, superseded by Microsoft Agent Framework) — if you want a Microsoft-ecosystem framework, evaluate MAF itself rather than legacy AutoGen, but be aware MAF is younger and more Azure/enterprise-flavored than LangGraph/CrewAI for this specific local-hobbyist use case.

## Notes on the aspirational return target

None of the above architecture choices materially change the statistical reality that a ~$650 account targeting 50%+ growth via manual day/swing trading on free-tier data faces very high variance and a nontrivial chance of loss; multi-agent LLM orchestration improves the *process* (structured reasoning, checks, auditability, memory of past calls) but does not change underlying market unpredictability or the well-documented tendency for retail day-trading strategies to underperform after costs. Treat the framework choice as an engineering decision about reliability/auditability of the analysis pipeline, not as something that itself produces edge.
