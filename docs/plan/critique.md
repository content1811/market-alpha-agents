Below is a prioritized critique. Each item names the concrete defect, why it matters, and a specific fix — not general praise.

## 1. (Critical) The orchestration section's actual reference code contradicts the agents section's architecture and reconciliation design
The `agents` section defines a 10-agent system with a strict "score ≠ confidence" convention (§0: "-0.9 score with confidence 0.2... must be treated very differently from -0.9 with confidence 0.8") and a detailed deterministic aggregation algorithm (§10.2: confidence-weighted blend, `vol_conf_multiplier`, stdev-based dispersion penalty, veto). But `orchestration/aggregate.py` in the orchestration section implements a *different, much simpler* 3-role system (`analyst`, `quant`, `risk` only — no MeanReversion/TrendMomentum/Seasonality/ShortSqueeze/OnChain/Derivatives/News as distinct graph nodes at all), with fixed weights `{0.3, 0.4, 0.3}` and:
```python
confidence = max(0.0, weighted_avg_abs_scaled(weighted_avg) * (1 - dispersion / 2))
```
This directly conflates confidence with the magnitude of the score itself — the exact anti-pattern the agents section's design principles explicitly forbid. It's unclear which of these two designs is the one actually being built.
**Fix:** Delete or explicitly label the orchestration section's `aggregate.py`/graph as "illustrative sketch, superseded by agents §10.2" — or, better, rewrite it to actually call all 10 specialists as nodes and implement the §10.2 algorithm verbatim so there is one authoritative aggregation implementation, not two incompatible ones.

## 2. (Critical, Japan-specific technical-analysis gap) No mention of TSE daily price-limit bands / special quotation (特別気配)
TSE stocks trade within a daily price-limit band around the previous close; when a stock hits the limit it can freeze into a special-quote state where stop and limit orders simply cannot execute at or beyond the band. Every ATR/structure stop-loss formula in `risk & validation` §1 and every RiskManagerAgent rule assumes stops are always fillable. For a ¥100,000 account concentrated in one or two JP positions, a single limit-lock day is a realistic, JP-specific tail risk this plan never models.
**Fix:** Add a `RiskManagerAgent` check: fetch/compute the daily price-limit band for JP tickers (published by TSE per price tier) and (a) widen or flag stops that fall outside the band as "may not be executable," (b) reduce position size or flag "limit-lock risk" for stocks near their limit, and note this explicitly in the alert template for JP tickers.

## 3. (High, rate-limit handling) JP equities have no real live-data fallback if the single unofficial source breaks
`config.yaml` lists `jp_equity_fallback: [yahoo_unofficial]` — but `yahoo_unofficial` *is* the primary intraday source too (`.T` chart endpoint), and J-Quants Free is stated to be 12-weeks-lagged and explicitly "reference-only, not live signal." So if Yahoo's unofficial endpoint gets throttled/blocked (which the plan itself calls "undocumented, throttled" and warns is "increasingly anti-scraping-hardened in 2026"), the entire JP-equity leg has zero live-data fallback — not degraded, *dead*. This is a materially weaker foundation than the US/crypto legs, and the plan doesn't surface that asymmetry to the operator.
**Fix:** Either (a) explicitly document that JP equities run at higher outage risk than US/crypto and define a "JP data unavailable" mode that forces all JP signals to `data_quality_flag=unavailable` / RiskManagerAgent veto, or (b) evaluate a second free JP source (e.g., Stooq JP tickers, or accept degrading to J-Quants-lagged-only "watchlist/backtest mode" for JP until live data returns) and wire that into `data/connectors/`.

## 4. (High, reconciliation/testability) Phase 6's "done" criterion is vague and contradicts the risk section's own concrete gate
Orchestration Phase 6 test criterion: "run for a minimum of several weeks to a few months." Risk & Validation §5 gives a precise, testable gate: "8–12 weeks of continuous forward-testing, or ~30 completed simulated trades, whichever is longer." Phase 6 should use that exact criterion as its literal Definition of Done instead of restating a vaguer version — as written, a builder could plausibly call Phase 6 "done" after 3 weeks, violating §5.
**Fix:** Replace Phase 6's test bullet with: "Phase 6 is not complete until §5's gate is met: ≥8–12 weeks AND ≥30 completed simulated trades per strategy, whichever is longer, with logged paper-vs-backtest Sharpe/PF comparison below the divergence threshold defined in §5."

## 5. (High, correctness bug) ADX "trend_confidence" formula contradicts its own stated thresholds
Both `MeanReversionAgent` and `TrendMomentumAgent` use `trend_confidence = clip((ADX-20)/30, 0, 1)`. But `TrendMomentumAgent`'s prose says "`>25` = trending, full weight" — yet at ADX=25 the formula gives `trend_confidence = (25-20)/30 = 0.167`, i.e. ~17% weight, not "full weight." Full weight (1.0) only occurs at ADX=50. This is a real internal inconsistency between the qualitative threshold table and the formula that computes it, affecting the two flagship directional agents' actual behavior at the exact ADX=20–25 boundary the design calls out as the critical regime switch.
**Fix:** Either change the formula to reach 1.0 by ADX=25–30 (e.g., `clip((ADX-15)/10, 0, 1)`) or rewrite the prose thresholds to match the actual formula output (state the real trend_confidence value at ADX=25, 30, 40 explicitly) — pick one and make the other match, then add a unit test asserting `trend_confidence(25) ≈ [documented value]`.

## 6. (High, missing TA topic) No handling of adjusted vs. unadjusted price series across data sources
yfinance, Twelve Data, Tiingo, and the Yahoo unofficial `.T` endpoint may return differently split/dividend-adjusted closes. None of the agents' indicator math (SMA/EMA crossovers, Bollinger, RSI-2, ADX, Donchian) specifies which convention `data/schema.py`'s `NormalizedBar` enforces. A stock split hitting mid-lookback with mismatched adjustment conventions between the live adapter and whatever the agent last cached would silently corrupt every MA/ATR/Donchian signal on that name for weeks.
**Fix:** Add an explicit `adjusted: bool` and `adjustment_factor` field to `NormalizedBar`, mandate one canonical convention (fully-adjusted close) in `schema.py`, and add an adapter-level test that verifies each source's data is normalized to it (e.g., feed a known historical split date and assert continuity).

## 7. (Medium-high, rate-limit gap) Stale/unavailable data isn't mechanically wired into agent confidence in the actual code
The shared schema has `data_quality_flag: ok|stale|partial|unavailable`, and §0 says agents should incorporate it, but neither `aggregate.py` nor the pipeline/cadence spec states a hard rule for *when* a cache-served value must be marked stale (e.g., "TTL exceeded by >2x ⇒ force stale," "primary+fallback both circuit-broken ⇒ unavailable ⇒ RiskManagerAgent auto-veto for that ticker"). Without this, the system can silently keep emitting confident-looking scores off hours-old cached data during an outage.
**Fix:** Add explicit rules to §2.4 of the data/alerting section: `data_quality_flag=stale` if age > 2×TTL (cap agent confidence ≤0.3), `unavailable` if primary+fallback both circuit-broken (agent abstains: `signal_score=0, confidence=0`, and RiskManagerAgent forces HOLD for that ticker), and add a Phase-1 regression test asserting this propagation.

## 8. (Medium, unrealistic-claim/citation gap) The FINRA Rule 4210 / June 4 2026 PDT-replacement claim is asserted with no citation
Unlike the Brazilian day-trader study and the MinervaScore arXiv paper (both cited with source IDs), the load-bearing regulatory claim underpinning the whole "$650 account can day-trade US equities post-PDT-rule-elimination" framing (`risk & validation` §2, referenced again in `agents` §9) has zero citation. If this is inaccurate or mischaracterized, the position-sizing/feasibility guidance for the largest asset-class leg (US equities) is wrong, and the plan's own "verify against 2026 current state" mandate is violated here specifically.
**Fix:** Add a source URL (FINRA rule filing/notice) for the Rule 4210 change and re-verify the effective date and actual mechanics (does it truly eliminate the $25k PDT threshold, or just modify margin requirements?) before this claim drives sizing logic.

## 9. (Medium, missing topic) No market-wide/macro regime circuit breaker distinct from per-trade ADX and post-loss drawdown breaker
`RiskManagerAgent` rule 7 only de-risks *after* the account has already drawn down ≥15%. There's no ambient-conditions breaker (e.g., a VIX-equivalent spike, a broad crypto-wide deleveraging event, or a JP market-wide circuit-breaker day) that reduces sizing/conviction *before* losses accrue — despite `CryptoDerivativesAgent`/`SeasonalityAgent` already computing pieces (liquidation clusters, F&G) that could feed such a signal.
**Fix:** Add a `MarketRegimeAgent`-lite check (even a simple config-driven rule: "if VIX-proxy/crypto-realized-vol > Nth percentile of trailing 1yr, halve all position-size ceilings system-wide regardless of per-ticker scores") consumed by RiskManagerAgent rule 3/6.

## 10. (Medium, human-workflow gap) `review_cli.py` conflates two distinct human interactions without specifying either fully
The orchestration/human-gate node's "approve/reject" is a pre-alert gate (should this recommendation even be sent?). Separately, `risk & validation` §5/§6 needs post-hoc outcome logging (`actual_outcome`, `human_action: followed|modified|ignored`) after the human has actually traded (or not) days/weeks later. The plan only describes one CLI surface (`ui/review_cli.py`) and doesn't specify whether/how it re-opens a past recommendation for outcome entry, how outcomes get matched back to the original `thread_id`, or what happens if the human never returns to log an outcome (does the fine-tuning loop just have a hole in its data?).
**Fix:** Split into two explicit CLI/flows in the design: `review_cli.py approve|reject` (pre-alert gate, same-day) and a separate `review_cli.py log-outcome <ticker> <date>` (backfills `outcomes.db` at any later date), with a defined "still pending outcome after 90 days" report so unlogged trades are visible rather than silently missing from the scorecards in §6.

## 11. (Low-medium, missing topic) Cross-sectional momentum universe is a small hand-picked watchlist, biasing the live ranking, not just the backtest
`risk & validation` §4 correctly requires point-in-time, survivorship-bias-free universes for *backtesting*. But `TrendMomentumAgent`'s live `xsect_score` percentile-ranks against "a defined universe (watchlist of 20–50 US tickers...)" — i.e., a small, static, self-selected list, not a broad index. A ticker can rank in the 90th percentile of a hand-picked 20-name watchlist while being mediocre against the actual market, silently inflating conviction.
**Fix:** Either benchmark `xsect_score` against a broad, cheaply-obtainable index proxy (e.g., an ETF's constituent return distribution, or simply the ticker's return vs. SPY/TOPIX/BTC rather than percentile-rank-within-watchlist), or explicitly document in the agent's rationale string that the percentile is "relative to your own watchlist, not the broad market" so the human doesn't over-read it.

## 12. (Low, polish on an otherwise well-handled item) 50%+ aspiration caveat isn't re-surfaced at the point of decision
`risk & validation` §7 is a genuinely strong, well-sourced treatment of the return aspiration. But that framing lives only in a static document — nothing in the actual alert templates (`data & alerting` §4.3) or the `PortfolioSupervisorAgent` output schema periodically re-surfaces realized-vs-aspirational performance to counter overconfidence after a lucky streak (the plan's own stated failure mode).
**Fix:** Add a monthly digest line (alongside the existing weekly/monthly recalibration cadence in `risk & validation` §6) that explicitly states realized CAGR/Sharpe-to-date next to the 50% aspiration and the Brazilian-day-trader base-rate framing, so the caveat is a recurring artifact, not a one-time document.
